# 단계 연결 초안 시험

## 팀원별 AI·자료 설정

저장소 루트에서 아래 명령을 한 번 실행한다. `.env.example`은 키 없는 공통 양식이고, `.env`에는 **각자 자기 Gemini API 키**를 적는다. `.env`는 Git에서 제외된다. 키를 채팅·커밋·실행 기록에 복사하지 않는다.

```powershell
cd C:\Users\admin\Desktop\haruharu
python -m pip install -r app/requirements.txt
Copy-Item .env.example .env
```

`.env`의 `GEMINI_API_KEY`를 채우고 필요하면 `GEMINI_MODEL`을 접근 가능한 모델로 바꾼다. 다른 팀원 PC에서도 저장소를 받은 뒤 같은 절차를 따라 실행한다. 이미 OS 환경변수로 설정했다면 그 값이 `.env`보다 우선한다. 키 없이도 저장된 결과 조회·수동 코스 수정·자동시험은 가능하며, 실제 AI 실행 버튼이나 `orchestrator.py`의 1·2단계 호출에는 해당 제공자의 인증이 필요하다.

`AI_PROVIDER=claude`로 바꾸면 기존 Claude 연결을 사용한다. `HARUHARU_DATA_DIR`과 두 CSV 파일명은 데이터 **위치**를 지정하는 설정이며, 관광 데이터 자체는 `.env`에 넣지 않는다. 현재 장소·이동 정보는 데모 CSV를 읽는다. 운영용 데이터 저장소 연결·실제 Gemini 출력 품질 검증은 별도 작업이다.

## 11/23 화면 보완 사용 순서 (AI 재실행 없음)

1. 저장된 기획을 선택하면 기본 조건과 제안 코스가 바로 표시된다. 기본 조건은 기존 1·2단계 선택을 이어받는다. 대상·지역·체류기간 변경 및 새 1·2단계 실행 화면은 이번에 추가하지 않았다.
2. 필요한 일정만 펼쳐 장소·시각을 수정하고 ‘수정한 코스 저장’을 누른다. 미정이 남아 있어도 초안 저장은 가능하다. 이전 코스를 보존하며 AI 재실행·자동 확정은 하지 않는다.
3. 전체 여행의 시작·종료를 바꿀 때만 ‘꼭 지켜야 할 시작·종료 조건 수정하기’를 열고 ‘시작·종료 변경 반영’을 누른다. 전체 여행의 시작 시각 변경은 기존 시간 조정 기능을 사용한다.
4. 운영시간·휴무·출처·출발일·세부 이동 확인·실행 이력·원문·검사는 접힌 ‘관리자 상세’에 있다. 기존 식사·운영 조건은 보존한다. 지원하지 않는 조건 변경을 기존 초안에 반영한 것처럼 표시하지 않는다. 저장된 운영자료는 실제 현장 운영을 새로 검증한 값이 아니다.
5. 지침의 확정 조건과 앱 추가점검을 구분한다. 3단계 지침의 주요 확정 조건은 시작·종료 확인, E7 노선 겹침 처리, 1박2일 오전 구성 선택이다. 기존 앱의 날짜·전 항목 운영 확인 요구는 더 엄격하며 이번에는 그 검사 로직이나 3·4단계 지침을 고치지 않았다. 상시 상품 확정 기준 및 앱 검사 정합성은 후속 검토가 필요하다.

기준은 사용자가 승인한 PR #10이 병합된 `integration/stage-1-5`이다. 이 문서는 담당자와 합의되지 않은 JSON을 운영 기준으로 확정하지 않는다.

## 실행 범위

```powershell
cd C:\Users\admin\Desktop\haruharu\app
python -m unittest discover -p "test_*.py" -v
python orchestrator.py
```

기본 실행은 1→2와 3단계 전달 검사까지다. 검사 통과 후 시작·종료·식사·식비·오전 구성·운영 방식을 담당자에게 묻고 `코스작성조건_선택.json`과 전달 JSON에 저장한다. 모르는 것은 Enter로 미정 유지. 실제 AI 사용에는 `.env`에서 선택한 제공자의 인증·모델 접근이 필요하다.

```powershell
python orchestrator.py --통합시험
```

이 옵션은 실제 3·4단계 AI 호출을 추가한다. 현재 개인 checkout에 3·4단계 파일이 없다면 호출 전에 대기 상태와 필요한 파일 경로를 기록한다. 최신 개인 수정과 통합 브랜치의 `지침/3_코스검토/`, `지침/4_홍보검토/`, `.claude/agents/코스검토.md`, `.claude/agents/홍보검토.md`, `.claude/skills/홍보문구/`를 함께 갖춘 환경에서 사용한다. 브랜치 전체를 덮어쓰지 않는다.

- 기본 실행의 입력·결과를 보존하고 별도 `통합시험_시각/` 폴더에 3·4단계 입력·원문·검사·담당자 선택을 기록한다.
- 3단계의 JSON·참조·확정 조건을 검사한 뒤 담당자의 실제 확인을 받아야 4단계를 호출한다. 오류·초안 선택이면 중단한다.
- 4단계는 문구·번역·배치 계획의 JSON 초안이다. 실제 이미지가 생성됐다는 뜻이 아니다. 번역 상태는 AI 초안이다.
- JSON 오류·AI 실패·없는 파일은 대기로 남긴다. 무한 재호출·자동 확정·5단계 호출은 하지 않는다.
- 원표 수치 대조, 4단계 문구·번역 검토, G5/G17 결정, 현장 운영 확인은 별도다.

## CRLF 확인

`test_코스조건`은 실제 CRLF 바이트 파일을 만들어 `에이전트_읽기`가 머리와 도구를 분리하는지 시험한다. 현재 `Path.read_text()`가 줄바꿈을 정규화해서 통과했다. CRLF를 확정 원인으로 간주한 코드 변경은 하지 않았다. 다른 문제가 생기면 BOM·파일 머리·실제 SDK 입력을 별도로 재현한다.

## 기존 2단계 결과의 전달 재검사

```powershell
python 기존결과.py "runs/20261122_131912/01회차"
```

AI 호출 없이 원문에 명시된 공통 설명과 묶인 관광지 표만 10열 근거 행으로 펼친다. 최신 2단계의 정상 출력은 처음부터 10열을 써야 한다. 기존 엄격한 전달 검사를 완화하지 않으며, 알 수 없는 축약 형식·누락된 공통 출처는 중단한다.

- 기존 실행 폴더를 덮어쓰지 않고 새 시각의 실행 폴더에 저장한다. 관리자 화면 새로고침 후 새 기록을 선택한다.
- E3와 확정 체류 기간은 저장된 담당자 선택을 사용한다. 원문에 남은 생성 당시의 ‘미선택’을 담당자 선택으로 취급하지 않는다.
- 새 전달 JSON에는 기존 2단계 원문과 원본 위치·해시를 보존한다. 원문에 적힌 수치의 정확성·원본 CSV와의 일치는 별도 검증이다.
- 전달 검사가 통과해도 3단계를 자동 실행하지 않는다. 시작·종료·식사·오전 구성·운영 방식의 코스 조건 입력 절차가 남는다. 모르는 항목은 미정으로 남겨 초안을 만들 수 있으나, 코스 확정과 구분한다.
- 이 재검사 명령 자체는 코스 조건 입력이나 저장된 결과에서의 AI 실행 재개를 하지 않는다. 아래 관리자 화면에서 이어서 실행한다. `orchestrator.py --통합시험`은 1단계부터 새로 실행하는 명령이다.

## 관리자 화면에서 기존 결과로 3단계 이어하기

```powershell
cd C:\Users\admin\Desktop\haruharu\app
python 관리자조회.py --port 8765
```

1. `http://127.0.0.1:8765/admin/`에서 **2→3 전달 검사 통과**한 기록을 선택한다. 예: 2026-11-22 22:33 재검사 기록.
2. **다음 단계 · 코스 조건 입력하고 3단계 시험하기**를 펼친다.
3. 시작·종료 장소/시각, 운영 방식, 치킨 옵션, 2일차 오전, 식사별 지정식/자유식·식당·식비 포함을 입력한다. 모르는 값은 비우거나 미정으로 남긴다. 당일은 2일차 항목이 없다.
4. **조건 저장**을 누른다. AI는 호출하지 않고 원본 회차 아래 새 `통합시험_시각/` 폴더에 조건과 3단계 입력 스냅샷을 저장한다. 입력을 바꾸면 다시 저장한다.
5. **3단계 AI 시험 시작**을 누른다. `.env`에서 선택한 Gemini 또는 Claude를 사용하며 사용량·비용이 발생할 수 있다. 3단계만 한 번 호출한다. 1·2·4·5단계와 담당자 확정은 실행하지 않는다.
6. 실행 중 상태가 갱신된다. 완료 후 **3단계 결과 보기**에서 시간표·식사·경고를 확인한다. 원문·JSON 탭에서도 조회할 수 있다. 형식·확정 준비 검사 실패라도 생성된 원문을 보존한다.

실행 실패는 선택한 AI의 키·모델 접근·SDK 설치·네트워크를 확인한다. SDK가 설치돼 있다는 사실만으로 인증·모델 접근까지 확인된 것은 아니다. 실패 후에는 조건을 다시 저장해 새 시험으로 시작한다. 서버를 끄거나 재시작하면 실행 연결이 끊긴 기록은 중단으로 표시된다.

조회 API는 그대로 사용하고 저장/시작 요청은 로컬 출처·세션 토큰을 검사한다. 원본 2단계 결과는 덮어쓰지 않는다. 이 화면은 아직 로그인·사용자별 권한을 갖춘 상용 서비스가 아니다.

### 설명문이 붙은 기존 3단계 결과 재검사

JSON 앞뒤에 SDK 진행 설명이 붙어 있어도 코드 블록이 하나이면 읽는다. 여러 블록 중 하나를 임의 선택하지 않으며 중복 키·잘못된 수치 상수 검사는 유지한다. 앱의 `코스시험.재검사(시험id)`는 저장된 원문과 입력만 사용하고 AI는 호출하지 않는다. 최초 상태·검사는 별도 사본으로 보존하고 새 검사·표시용 구조화 JSON을 저장한다. 재검사는 서버 측 작업이며 관리자 화면에서 조건 저장·AI 시험 시작을 다시 누를 필요가 없다.

화면에서 ‘검사 확인 필요’가 남더라도 시간표와 경고는 조회할 수 있다. JSON을 읽을 수 있다는 것과 코스 확정 조건이 충족됐다는 것은 다르다.

앱 형식·연결 검사와 담당자 확인 대기는 별도로 표시한다. 입력하지 않은 시작·종료 정보는 대기이며, `25:00` 같은 잘못된 시각은 형식 오류다. 2일차 점심 포함 여부를 종료 시각 때문에 결정하지 못한 경우에는 선택값을 보존하고 확인 대기로 남긴다. 담당자가 선택한 자유시간에는 관광지 수요 근거를 요구하지 않는다. 미확인사항의 `대상 칸ID` 별칭도 읽되 실제 없는 칸은 계속 오류다.

결과 보기에서는 Markdown 결과와 구조화 JSON 모두 시간표로 표시하고, ‘원문 · JSON’ 탭에서 원본 내용을 조회한다. 표시 수정 후에는 브라우저를 새로고침한다. 저장된 결과를 보는 데 조건 재저장·AI 재실행은 필요하지 않다.

### AI 없이 기존 초안 수정 반영

1. 기존 코스 결과가 있는 저장된 시험을 선택한다.
2. 시작·종료 장소와 시각을 수정하고 **2일차 점심 포함 여부**를 포함/미포함/미정에서 선택한다. 당일은 해당없음이다.
3. **기존 초안에 수정 반영 (AI 없음)**을 누른다. 새 AI 시험용 조건 저장·AI 시작을 누를 필요가 없다.
4. 새 수정본의 시간표와 변경 목록·재검토 항목을 확인한다. 이전 초안과 그때의 입력은 보존된다.

점심 포함 시 기존 칸이 없으면 시각·권역·이동시간 미정인 식사 칸을 추가하고 기존 자유식/식비 선택을 반영한다. 미포함이면 해당 칸만 제외하고 선택 이력은 남긴다. 미정이면 기존 시간표를 유지하며 포함 여부를 확인 대기로 둔다. 후보 식당·지정 식당을 자동으로 만들지 않는다.

이 기능은 시작·종료 및 2일차 점심을 수정한다. 운영 방식·치킨 옵션·2일차 오전·1일차 식사 변경이 섞이면 중단하고 알려준다. 2026-11-23 보완으로 시작 시각에 맞춰 시작일의 가정 시각을 이동한다. 이동·영업 조건은 재계산하지 않으므로 시작·종료와 일정 사이, 점심과 종료 장소 사이를 재검토해야 한다. AI가 작성한 이전 메모는 수정 전 기록임을 화면에 표시하고 코스 확정을 대신하지 않는다. 4단계는 실행하지 않는다.

### 시작·종료 일차와 시간표 충돌

시작과 종료 각각 일차(1일차/2일차/미정)를 고른다. 당일은 1일차만 지원한다. 기존 기록에는 이 값이 없으므로 일차를 추측하지 않고 선택 대기로 표시한다. 일차·시각을 고른 뒤 ‘기존 초안에 수정 반영 (AI 없음)’을 누르면 선택한 일차가 수정본에 저장되고 재검사된다.

검사 항목은 시작 전 일정, 종료 후 일정, 명시된 머무는 시간이 종료를 넘는 일정, 같은 안의 일정 시간 겹침이다. 시각·머무는 시간이 미정이면 검사 대기로 남긴다. 일차 미정일 때의 조건부 충돌은 참고로 따로 표시하며 확정된 충돌로 취급하지 않는다. 예를 들어 1일차 20:00은 2일차 18:34 종료보다 앞서지만, 1일차 18:34 종료보다 늦다.

검사는 표시된 시각과 머무는 시간만 비교한다. 이동·영업시간을 새로 조회하지 않는다. 수동 수정 시의 가정 시각 이동과 시간 충돌 검사는 구분한다. 코스 결과 상단·전달 검사·시험 상태에서 충돌과 검사 대기를 볼 수 있다.

시작 정보와 종료 정보는 각각 일차·장소·시각을 묶어 입력한다. ‘지금 선택한 값’은 현재 폼 값이며 ‘저장된 값’은 서버에서 읽은 값이다. ‘기존 초안에 수정 반영 (AI 없음)’ 또는 조건 저장 후에는 저장 파일을 다시 읽어 일차가 같은지 확인한다. 두 요약이 다르면 아직 반영하지 않은 변경일 수 있고, 저장 재조회 값이 요청값과 다르면 오류로 알린다. 기존 실제 기록의 미정 일차를 시험값 1·2로 바꾸지 않는다.

일차 선택 전의 빈 항목은 미정과 구분한다. 반영 버튼을 누르면 필요한 일차 입력을 버튼 아래에서 안내하고 저장 요청은 보내지 않는다. 미정 초안으로 저장하려면 ‘미정으로 저장 (초안)’을 직접 선택한다. 기존 미정 기록을 불러오면 일차 선택을 다시 요구한다.

저장본 선택지는 ‘최신/이전 · 저장본 번호 · 저장 시각 · 상태’로 표시한다. 검사와 결과 위에도 선택한 저장본의 정보·기록 번호가 보인다. 3단계 파일·전달 검사는 선택한 저장본 하나만 조회하며, 과거 저장본은 선택지를 바꿔 확인한다. 결과 보기·새로고침으로 선택한 과거 저장본이 최신본으로 자동 바뀌지 않게 유지한다.

### 11:34 시작에 맞춘 시간 조정

기존 첫 일정이 10:00이고 새 시작이 11:34이면 시작일의 가정 시각에 94분을 더한다. 예: 점심 11:41→13:15, 오후 13:16→14:50, 저녁 18:00→19:34, 밤 20:00→21:34. 식사목록 시각도 해당 칸과 맞춘다. 반복 반영 시 현재 첫 시각을 기준으로 하므로 같은 시작 시각을 다시 반영해도 시간을 또 더하지 않는다.

확정 예약·다음 날의 기존 시각·미정 시각은 임의로 움직이거나 채우지 않는다. 일차가 미정이면 기존 일정 일차를 유지하고 시각만 옮기며 일차 선택 대기를 남긴다. 머무는 시간·일정 간 간격을 보존하므로 늦춰진 식사·야시장의 운영시간, 시작 장소와 첫 관광지 사이 이동은 반드시 재확인한다. 조정으로 체류 기간 밖으로 나가면 일부만 바꾸지 않고 저장 전에 알려준다.

일차 미입력 때문에 비활성 버튼을 눌러도 아무 안내가 없던 경로를 보완했다. 저장 진행·실패·완료가 버튼 아래에도 표시된다. 서버 재시작으로 세션 토큰만 만료된 요청은 새 토큰으로 한 번 재시도하며 다른 오류는 자동 재요청하지 않는다.

## 운영시간·숙박·자유시간 확인과 4단계 준비 검사

1. 결과가 있는 저장본을 선택한다. 위쪽 시작·종료 일차·장소를 먼저 수정 반영한다.
2. **운영시간·숙박·자유시간 확인하고 반영하기 (AI 없음)**를 펼친다. 방문 시작일을 입력한다.
3. 일정 항목을 펼쳐 시작·종료 일차와 시각, 장소·권역, 이후 연결·확인 메모를 입력한다. 숙박은 예를 들어 1일차 밤→2일차 아침으로 정할 수 있다. 야시장처럼 운영시간에 맞춰 체류를 줄여야 하는 일정도 이곳에서 기간을 수정할 수 있다. 입력한 기간으로 머무는 시간과 식사 시각을 맞춘다.
4. 장소·자유식 후보별 운영/휴무, 영업시간, 주문·입장 마감(또는 명시적 해당없음), 출처 구분·자료명/URL·실제 확인일, 방문일 운영 확인을 입력한다. 다음 날 끝나는 영업은 별도 체크한다. 자유식 후보만 명시적으로 제외할 수 있고 관광 일정을 자동 삭제하지 않는다.
5. E7 겹침 처리와 확인 메모를 입력하고, 실제로 검토한 뒤 담당자 최종 확인을 체크한다. 최종 확인은 새 저장 때마다 직접 체크한다.
6. **확인 결과 반영·4단계 준비 검사 (AI 없음)**를 누른다. 새 수정본의 결과·검사에서 남은 항목을 확인한다. 일부 미정이어도 확인 필요 상태로 저장할 수 있다.

검사는 입력된 출처·날짜·운영 여부와 일정의 일관성을 대조한다. 실제 웹사이트·전화·현장을 자동 확인한 것이 아니다. 날짜·일정이 바뀌면 이전 확인을 그대로 완료 처리하지 않는다. 준비 완료에는 시간 충돌/미정 해소, 운영시간/마감 범위, 방문일 운영 확인·출처, 이동 연결, E7 처리와 담당자 최종 확인이 필요하다. 기존 R/W 경고는 보존한다.

검사 통과와 담당자 최종 확인이 함께 있으면 4단계 준비 완료로 표시하고 실제 입력에 근거한 확인 기록을 남긴다. 4단계 AI를 호출하지 않는다. 원본 코스·입력은 보존하고 운영 확인 입력은 `3단계_운영확인.json`, 반영 결과는 새 `3단계_결과.md`·구조화 JSON, 준비 여부는 전달 검사와 상태 JSON에 기록한다.
