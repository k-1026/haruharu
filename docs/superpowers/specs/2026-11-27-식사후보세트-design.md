# 식사 후보 설계 (저녁 정식 후보 세트 + 점심 선택 사항)

작성일 2026-11-27 · 상태: 초안, 사용자 승인 대기 · 규모: 프로젝트(직원 화면·서버·지도·관광객 미리보기에 걸침)

## 1. 의도와 이유

- 치킨(치맥)으로 저녁 체류를 늘리는 것이 핵심이다. 그래서 식사 후보에 치킨을 반드시 넣는다. 치킨 식사는 저녁 선택 옵션 1번까지라는 팀 규칙은 유지한다(낮에 치킨 식사 금지).
- 관광객이 치킨을 원하지 않을 수 있으므로, 설문에서 선호가 높은 메뉴의 식당도 함께 제공한다.
- 직원은 식당 한 곳을 확정하지 않고 후보 세트를 구성하며, 관광객이 세트에서 한 곳을 고른다. 식당 결제는 개별 결제이다.
- 현재 문제(1127 실패 문서 기준): ① 점심은 "후보 묶음", 저녁은 "한 곳 확정"으로 방식이 갈려 있다. ② 점심 체크박스에 "선택 불가" 후보도 체크된다(저장 시점에야 서버가 거절). ③ 직원 설정과 관광객 선택 미리보기가 한 화면에 섞여 있다. ④ 관광객 QR의 선택 연결은 미완료.

## 2. 목표 / 비목표 / 실패 기준

목표
- 저녁은 정식 후보 세트(저장 → 관광객 선택)로 동작한다. 점심은 선택 사항(참고 추천만 보여 주고 "자유롭게 해결"도 고를 수 있음)으로 둔다.
- 저녁 세트는 치킨 후보 1곳 이상을 필수로 포함한다(더 많아도 됨).
- 후보는 직전 장소에서 너무 멀지 않은 식당 위주로 시스템이 제안하고, 직원은 검토·수정한다.
- 지도에서 후보가 권역 안 핀으로 한눈에 보이고, 선택하면 경로와 이동시간이 나온다.
- 서문시장 같은 시장은 식당이 아닌 구역형 후보로 별도 표시한다.

비목표
- 관광객 QR 화면의 실제 연결(별도 작업, 이번엔 직원 쪽 정리와 미리보기 분리까지).
- 서문시장 내부 식당 목록 조사.
- 식당 예약·지정식 확정.

실패 기준(기술적으로 동작해도 실패): 치킨 없이 저장됨 / 선택 불가 후보가 체크됨 / 확인되지 않은 구역형 후보가 "바로 담기 가능"으로 표시됨 / 공통 코스가 관광객 선택으로 바뀜.

## 3. 접근 방식 (검토한 안)

- 저녁(채택): 정식 후보 세트, 시스템이 제안 + 직원 수정.
- 점심 처리안 비교(제 주관 점수, 35점 만점): 점심 제거 26점 / 점심 선택 사항 31점(채택) / 점심도 정식 세트 21점. 제거는 낮 12~14시가 비어 이동시간이 어긋나고 낮 먹거리를 못 보여 주며, 정식 세트는 규칙·화면이 두 배가 되고 미확인 정보 노출 위험이 크다.
- 점심 외 안 기각 사유(저녁 방식 비교):
- B안: 점심의 선택 불가 체크만 막기. 방식 차이가 남아 요청 해결 안 됨 → 기각.
- C안: 권역 단위 묶음. 식당별 이동 검증을 새로 설계해야 해 범위가 큼 → 기각.
- 사용자와 대화에서 저녁 방향과 점심 선택 사항안을 확정했다(2026-11-27).

## 4. 결정된 사항 (사용자 결정)

1. 치킨 후보는 저장 필수(1곳 이상, 상한 없음). 주로 저녁.
2. 저녁 직전 동선에서 너무 멀지 않은 식당 위주.
3. 설문 선호 메뉴 식당도 세트에 포함(가상 설문 예: 불고기·구이 45%, 국수 25%, 한식 백반 20%, 치킨·닭요리 10%).
4. 시스템이 세트를 제안하고 직원이 검토·수정한다.
5. 서문시장은 구역형 카드로 따로 표시. 현재 점심 칸에 "자유식 · 중구 서문시장"이 기준 장소로 들어가 있음(사용자 확인).
6. 점심은 동선에서 빼지 않고 시간 블록을 유지하되 선택 사항으로 둔다(관광객이 안 먹고 싶을 수 있음).

## 5. 설계

### 5-1. 후보 분류(서버, 기존 `비교`의 상태 활용)
- 바로 담기 가능 / 확인 후 담기(경고 있음) / 담을 수 없음(오류 있음).
- 담을 수 없는 후보는 체크 불가, 사유만 접힌 영역에 표시. 점심의 기존 허점(체크 후 서버 거절)을 화면에서 막는다. 서버 검증은 그대로 유지한다.

### 5-2. 세트 제안(서버, 신규)
- 입력: 식사 칸(점심/저녁), 직전·다음 장소, 조건(지역·설문 선호 메뉴).
- 거리 기준: 기존 권역 반경(기본 1500m) + 직전 장소 도보 N분 이내. N 기본 15~20분은 구현자 임의 제안이며 직원이 조절 가능(미확정 값으로 표시).
- 채우는 순서: 치킨 후보(가까운 순) → 설문 상위 메뉴별 후보(가까운 순). 점심에는 치킨 식사를 넣지 않는다(기존 규칙 유지).
- 저녁 세트 저장은 치킨 후보 0개면 거절. 점심은 해당 없음.
- 후보 수 제한은 기존 2~12개 유지.

### 5-2-1. 점심(선택 사항)
- 점심 시간 블록(시각·앞뒤 이동시간)은 유지한다.
- 점심에는 치킨 필수, 설문 메뉴 규칙, 후보 최소 개수(현재 2개 이상) 규칙을 적용하지 않는다. 치킨 식사는 기존 규칙대로 불포함.
- 관광객 선택지에 "자유롭게 해결"을 항상 둔다.
- 직원이 점심 참고 추천을 저장하면 그 후보를 보여 주고, 저장하지 않으면 점심 칸은 "점심 시간(자유)"만 표시한다(제가 정한 값).
- 식사 기준 장소가 시장(서문시장)이면 구역형 카드(5-3)를 쓴다.

### 5-3. 구역형 후보(시장)
- 장소유형이 시장인 후보 또는 식사 기준 장소가 시장이면 "구역형" 카드("서문시장 안에서 먹기 · 구체 식당은 현장 선택").
- 구역형은 치킨 필수 조건에 세지 않고, "바로 담기 가능"으로 표시하지 않는다("구체 식당 미수집" 표시).
- 같은 시간대에 시장이 이미 방문 장소면, 후보 목록에서 중복을 막고 "시장 먹거리 + 주변 식당"으로 묶는다.
- 서문시장이 실제 데이터에 식당/관광지 어느 항목으로 있는지는 구현 전 확인 필요(미확인).

### 5-4. 직원 화면
- 저녁: 정식 세트 화면. 메뉴별 그룹(치킨 필수 그룹 먼저, 설문 상위 메뉴 그룹). 점심: 가벼운 참고 추천 화면(체크 필수 규칙 없음).
- 직원 설정 영역과 "관광객 화면 미리보기"를 분리. 미리보기는 QR 연결 전까지 "시연용" 표시.

### 5-5. 지도
- 식사 칸은 권역 원 안에 후보 핀 여러 개(치킨은 다른 색). 핀 선택 시 직전 → 식당 → 다음 경로와 이동 분 표시(기존 `비교`의 후보이동 재사용).
- 관광객 선택은 해당 관광객 지도에만 반영, 공통 코스는 불변.

## 5-6. QR 담당자에게 전달하는 약속(인터페이스)
QR 담당자는 직원 화면 내부를 몰라도 되고, 아래 조회 결과만 보고 화면을 만든다.
- 조회: `GET /api/plan/meal/options` (기존). 결과의 `식사묶음` 목록, 항목마다 `칸ID`(점심/저녁 칸), `후보[]`, `공개준비`.
- 후보 한 개의 필드: `장소명`, `이름`, `치킨`(true/false), `구역형`(신규, 시장), `선택가능`, `오류[]`, `확인필요[]`, `좌표`, `후보이동[]`(직전→식당→다음 이동 분·경로), `메뉴그룹`(신규, 분류 가능할 때만).
- QR 화면 규칙: ① 저녁은 `공개준비`가 true인 세트만 관광객에게 보인다. 점심은 후보가 없어도 "점심 시간(자유)"로 표시하고 "자유롭게 해결"을 항상 둔다. ② `선택가능`이 false인 후보는 숨기거나 비활성. ③ `구역형`은 "구체 식당은 현장 선택" 문구와 함께 별도 카드. ④ 치킨 후보를 먼저 노출하고 메뉴 그룹별로 묶는다. ⑤ 관광객 선택은 그 사람의 개인 지도에만 저장하고 공통 코스·직원 세트는 바꾸지 않는다.
- 이번 작업 범위: 위 필드를 조회 결과에 정확히 채워 주는 것과, 직원 화면의 "관광객 화면 미리보기"가 같은 필드를 쓰게 하는 것. 실제 QR 화면 제작은 QR 담당자 몫이다.
- 전달물: 이 문서의 5-6절 + 실제 조회 결과 예시 JSON 1개를 구현 후 `정리본/`에 함께 둔다(위치는 제안, 확정 아님).
- 확인 필요: QR 담당자가 이미 정해 둔 필드명이 있는지(있으면 그 이름에 맞춘다).

## 6. 제약
- 기존 점심 후보 묶음 저장 API·데이터 구조(`후보묶음`)를 확장해 재사용하고, 기존 저장 데이터와 호환 유지. 점심의 "2개 이상" 최소 규칙은 완화·제거가 필요하다(`묶음반영`).
- 저녁의 기존 "한 곳 확정" 경로는 후보 세트로 대체. 이전에 확정된 저녁 데이터를 어떻게 이관할지는 구현 계획에서 정한다.
- 설문의 음식 선호는 식당 메뉴·예약 가능성의 증명이 아니다(유저플로우 v2 기준).
- 파일 수정은 개인 브랜치, 커밋은 사용자 확인 후.

## 7. 구현자에게 남기는 것
- N분(도보) 기본값, 메뉴 그룹 이름 분류(식당 데이터의 메뉴 정보 유무 확인 필요), 기존 저녁 확정 데이터 이관 방식, 시험(`app/시험/test_코스편집.*`) 갱신.
- 식당 데이터에 메뉴 분류 열이 없으면 설문 메뉴 매칭이 불가능하다. 이 경우 치킨 여부(`치킨 옵션` 표시)만으로 시작하고 메뉴 분류는 후속으로 둔다(구현 전 확인).

## 8. 이 문서에서 내가 정한 값(검토 요청)
- 도보 15~20분 기본값 / 구역형은 치킨 조건에 불산입 / 점심에 치킨 불포함 유지 / 저녁 세트 저장 시 치킨 필수 검사는 서버에서 수행.
