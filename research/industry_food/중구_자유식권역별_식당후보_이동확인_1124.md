## 1. 먼저 이해할 내용

코스에는 ‘저녁 자유식 시간과 권역’을 넣고, 그 안에 여러 식당을 참고 후보로 보여준다. 관광객은 다른 식당을 골라도 된다. 여러 권역을 모든 관광객이 차례로 방문하는 구조가 아니다.

예: ‘북성로 일대에서 자유식 → 정해진 시각까지 서문야시장 약속 장소 도착’. 한성불고기와 원조북성로우동불고기를 함께 안내하되, 각각의 이동시간을 따로 붙인다. 같은 권역이라고 같은 이동시간을 쓰지 않는다. 만나는 장소·시각은 아직 미정이다.

이 원칙은 저장소 `inventory/유저플로우_v1.md`의 식사 흐름과 `지침/3_코스검토/3_코스_짜기.md`의 자유식 규칙에 이미 있다. 이번 조사 때문에 새로 한 곳을 고정할 필요가 없다.

## 2. 음식 후보를 고른 근거

저장소 `research/data/외국인/대구_외국인추천음식상위20_2024.csv` 기준이다. 문항은 ‘추천 음식’이며, 단순한 개인 선호도 조사나 특정 가게 만족도 조사가 아니다.

| 음식 | 전체 1,010명, 1+2순위 | 일본 거주 응답자 83명, 1+2순위 | 이번 시연에서의 활용 |
|---|---:|---:|---|
| 불고기 | 18.0% | 19.6% | 우선 비교할 식사 후보군 |
| 찜갈비 | 9.3% | 6.3% | 기존 코스를 살리는 대안 후보군 |
| 닭튀김/치킨 | 3.8% | 1.7% | 원하는 경우 선택 |

이 수치는 ‘일본인 커플은 반드시 불고기를 먹는다’는 뜻이 아니다. 일본 응답자 표본은 83명이며, 일본×가을×커플 교차 결과가 아니다. 설문의 불고기 범주가 아래 돼지 연탄불고기 가게의 선호까지 직접 입증하지도 않는다. 음식군 탐색 근거로만 사용하고, 고기 종류·양념·식이 제한은 별도로 안내해야 한다.

## 3. 자유식 권역별 복수 후보

아래 권역은 안내를 위한 실무상 묶음 제안이며 공식 지정 구역이 아니다. 아직 정확한 경계·집결점이 정해지지 않아 권역 전체에 대한 이동시간은 확정하지 않았다.

| 자유식 권역 | 함께 안내할 후보 | 현재 가능한 것 | 아직 필요한 것 |
|---|---|---|---|
| 북성로·서성로 일대 | 한성불고기 / 원조북성로우동불고기 | 두 식당의 지도 위치·앞뒤 이동 참고값 제공 | 권역 경계와 출발·합류 지점, 영업·주문 조건 최종 확인 |
| 대구역 남쪽·교동 일대 | 운수좋은날 불갈비 | 기존 ‘북성로1가 연탄 불고기집’ 기록과 전화번호가 같은 지도 후보 확인 | 주소 84/84-1·이전 여부 확인. 이 권역은 두 번째 식당이 아직 없어 **복수 후보 권역으로는 보류** |
| 동인동 찜갈비골목 일대 | 산호찜갈비 / 봉산찜갈비 | 기존 찜갈비안 유지, 공식 안내 비교 | 봉산 앞뒤 경로, 산호 경로의 같은 조건 재조회, 맵기 조절·최소 주문 확인 |
| 동성로·종로 일대, 치킨 선택 | 뉴욕통닭 / 원주통닭 | 저장소의 두 중구 후보를 선택 목록으로 유지 | 최신 영업·주문 마감·휴무 확인, 원주 앞뒤 경로 확인 |

북성로와 교동을 넓게 묶어 세 곳을 한 목록에 보여줄 수는 있지만, 안내 범위를 넓히면 걷는 부담도 커진다. 현재는 북성로 2곳을 한 묶음으로 두고 운수좋은날은 위치 확인 뒤 인접 대안으로 표시하는 편이 명확하다. 빈칸을 채우려고 설문 근거가 약한 음식을 임의로 추가하지 않는다.

## 7. 매번 검색하지 않도록 자동화할 수 있는가?

**가능하다. 사람이 식당마다 길찾기를 반복하는 구조를 완성형으로 삼을 필요가 없다.** AI에게 분 단위 시간을 상상하게 하는 대신, 길찾기 서비스를 호출해 받은 숫자로 검사하고 AI는 이유를 설명하게 한다.

권장 흐름:

1. 식당 이름·주소·좌표·지도 ID를 연결한다. 동명이점·이전 후보는 먼저 확인 대상으로 돌린다.
2. 이전 관광지→각 후보, 각 후보→다음 관광지를 자동 조회한다. 이번 3개 식당은 편도 6구간, 도보·대중교통을 따로 조회하면 예시상 최대 12건이다. 모든 장소의 모든 조합을 매번 계산할 필요는 없다.
3. 반환된 시간·걷는 양·환승 수로 일정에 맞는 후보를 고른다. 경로 실패·영업 미확인 값은 빈칸과 확인 요청으로 남긴다.
4. 화면에는 ‘자유식 권역 + 여러 후보 + 각 후보 이용 시 이동 참고값’을 표시한다. 다른 식당을 고른 관광객에게까지 이 시간을 보장하지 않는다.
5. 같은 구간의 결과는 제공사 약관이 허용하는 범위·기간 안에서 재사용한다. 장소·이동수단·출발 날짜/시각 조건·정렬 방식·제공사·조회일을 함께 기록한다. 장소나 일정이 바뀌면 영향을 받는 구간만 다시 조회한다.

### 공식적으로 확인한 연결 방법

| 방법 | 공식 문서에서 확인한 내용 | 프로젝트 적용 전 확인할 것 |
|---|---|---|
| TMAP 대중교통 API | 출발·도착 좌표로 대중교통 경로와 보행 연결 정보를 제공. 앱 키 필요. 검색 날짜/시각 `searchDttm` 항목 있음 | 대구 범위·요청 시각 지원 범위·대기시간의 의미·요금·한도·저장/표시 조건 |
| TMAP 보행자 경로 API | 도보 경로 안내용 별도 API 제공 | 총시간·거리·계단 등 필요한 응답, 요금·한도·표시/저장 조건 |
| ODsay 대중교통 API | 대중교통 경로 조회 가능. 다만 운영사 2026-05-21 답변은 `searchPubTransPathT`가 정적 정보 기반이라 지정 출발시각의 대기시간 포함 결과를 제공하지 않는다고 설명 | 도입할 API/상품의 현재 사양 재확인. 네이버 실시간 화면과 동일한 값이라고 표시하지 않음 |

추천: 우선 TMAP 공식 API를 검토해 도보와 대중교통을 같은 제공사 기준으로 연결하는 방안을 비교한다. 실제 상품 사양·한도·비용을 확인하기 전 채택 확정이나 무료·실시간 정확도 보장은 하지 않는다. 네이버 화면의 숫자와 다른 API의 숫자를 같은 조건의 값처럼 섞지 않는다.

‘자동 이동 조회’와 ‘식당이 오늘 정말 영업하는지 확인’은 다른 문제다. 경로는 자동 조회가 가능하지만, 갑작스러운 휴무·이전·단체 수용 같은 예외는 운영 공지나 전화 확인이 남을 수 있다. 사용자는 모든 후보를 매번 검색하는 대신 **자동 조회가 실패했거나 자료가 충돌한 항목**을 확인하면 된다.

당장은 이 MD의 확인값으로 시연 자료를 준비하고, 기존 핵심 기능 시연이 안정된 뒤 ‘길찾기 API 연결’을 별도 작업으로 붙이면 된다. 이번에는 API 등록·키 발급·요금제 선택·코드 연결을 하지 않았다.
